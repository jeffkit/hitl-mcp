Architecture Topology

企微 AI Bot · HITL Server 架构拓扑
公众机器人版（远程服务版）与 hitl-mcp 客户端

本文基于 hil-mcp monorepo 源码，描述「企业微信 AI 机器人」作为消息通道时， 远程共享部署形态（代码中即 HITL_SHARED_MODE=true，又称公众机器人版 / 远程服务版） 下的整体拓扑，以及 MCP 客户端 hitl-mcp（npx hitl-mcp）如何与之协作。

涉及代码：packages/hitl-server（Python 后端） · packages/mcp-server-ts（TS MCP 客户端） · 引擎：hitl_server/engines/wecom_aibot.py · 协议参考： 企微 AI Bot 接入文档

一、整体拓扑

远程服务版与本地单机版在代码上是同一套，差异仅在 部署位置 与 鉴权 / 路由策略。 下图展示多人共享一台远程 hitl-server、共用一个企微 AI Bot 的拓扑：

MCP / 请求下行 响应 / 回复上行 HTTPS + Bearer 鉴权 企微 WebSocket 长连接 管理台
「公众机器人版 / 远程服务版」的本质：仍是同一个 hitl-server 二进制，只是 ① 部署在公网 / 内网服务器上（HITL_HOST + nginx 反代）； ② 开启 HITL_SHARED_MODE=true，强制 /api/* 鉴权、 禁止回退到全局最近活跃收件人，从而让一个企微 AI Bot 安全地服务多个开发者。

二、三层职责划分

① 客户端

AI Agent + hitl-mcp

运行在每个开发者本机。Agent 通过 MCP(stdio) 调用 hitl-mcp 暴露的两个工具： send_and_wait_reply 与 send_message_only。

  • 不持有任何微信 / 企微长连接
  • 把工具调用翻译为对远程 hitl-server 的 HTTP 请求
  • 轮询 /api/poll/<session_id> 取回复，交回 Agent
  • 共享模式：请求带 Authorization: Bearer <api-key>，--chat-id 必填

代码：packages/mcp-server-ts/src/

② 后端

hitl-server（远程常驻）

单进程 FastAPI 服务，是整个系统的中枢：

  • 进程内维持企微 AI Bot 的 WebSocket 长连接（订阅 / 心跳 / 断线重连）
  • 会话管理：分配 [#short_id]、引用回复精确匹配、FIFO 降级、超时清理
  • API 鉴权：HITL_API_KEY 单 key 或 HITL_API_TOKENS 多租户白名单
  • 管理台 /console：填凭证、看引擎状态、调试会话

代码：packages/hitl-server/hitl_server/

③ 通道

企业微信 AI Bot

消息通道由企微开放平台提供，只有一个 Bot（公众机器人），全员共用：

  • 连接：wss://openws.work.weixin.qq.com
  • 鉴权：aibot_subscribe 带 bot_id + secret
  • 收：aibot_msg_callback → 单聊按 from.userid、群聊按 chatid
  • 发：aibot_send_msg（markdown），收件人即 chatid

协议：path/101463

三、公众机器人版（共享模式）的关键机制

共享部署的核心难题是：一个 Bot、一台 Server，如何安全地服务 N 个开发者，且不让 A 的确认请求发到 B 的会话里。 代码用三道闸门解决：

闸门 1

API 鉴权（防冒充）

共享模式下 /api/* 强制带 Bearer Token（handlers/auth.py）：

  • HITL_API_KEY：单一 key，持有者可发任意 chat_id（可信单租户）
  • HITL_API_TOKENS：JSON {token: [chat_id, ...]}，做 chat_id 白名单绑定
  • 越权请求一律 403，token 缺失 / 非法 401
闸门 2

chat_id 必填（防串扰）

非共享模式下，chat_id 为空会回退到「最近活跃收件人」。共享模式下禁止回退：

  • /api/send：空 chat_id 直接拒绝 shared_mode_missing_chat_id
  • WecomAibotEngine.send_message：shared_mode 下同样拒绝
  • MCP 端 --shared 且无 recipient → 本地直接报错，不发请求
闸门 3

自助获取 chat_id（防门槛）

新用户如何知道自己的 chat_id？共享模式有自动回告机制：

  • 用户首次在企微给 bot 发纯文本消息（非引用回复）
  • 引擎 _reply_chat_id() 把该会话的 chat_id 回复给用户
  • 用户把它填进 MCP 配置 --chat-id，之后 AI 请求精确发到该会话
  • _welcomed 集合避免重复回告（进程重启后会再回告一次）
凭证归属：共享模式下，bot_id / bot_secret 由运维在服务端（环境变量或管理台） 统一持有。普通用户的 MCP 配置不应带 --bot-id / --bot-secret， 也不应调用 /api/engines/wecom-aibot/start（该接口受 API Token 鉴权保护，避免凭证覆盖导致 WS 互踢）。

四、一条消息的完整旅程

以开发者 A 让 AI 执行 send_and_wait_reply 为例，从 Agent 调用到拿到回复的全链路：

Agent 调用工具 send_and_wait_reply({ message, recipient: chat_id_A })
📍 AI Agent · MCP(stdio)
hitl-mcp 转 HTTP：POST /api/send，body 带 message / chat_id / wait_reply=true / bot_key / upstream=wecom-aibot， header 带 Authorization: Bearer <A 的 api-key>
📍 mcp-server-ts/src/engines/wecom-aibot.ts · sendAndWait()
鉴权 + 白名单校验：require_api_token 校验 Bearer → 返回该 token 允许的 chat_id 列表； ensure_chat_id_allowed 确认 chat_id_A 在白名单内，否则 403
📍 hitl-server/handlers/auth.py + api.py
引擎路由 + 创建会话：engine_manager.get_by_bot_key/upstream 找到 WecomAibotEngine； storage.create_session() 生成 session_id 与 short_id（前 8 位），状态 waiting
📍 engines/manager.py + storage.py
拼接消息头并下发：引擎 _format_message_with_header 拼成 [#short_id 项目名]\n消息正文\n\n> 请引用回复此消息，通过 aibot_send_msg（markdown）发到企微
📍 engines/wecom_aibot.py · send_message()
hitl-mcp 开始轮询：拿到 session_id 后循环 GET /api/poll/<session_id>（默认 2s 间隔）
📍 mcp-server-ts/src/engines/wecom-aibot.ts · _pollReply()
用户在企微回复（建议「引用回复」）：企微回调 aibot_msg_callback 经 WebSocket 进入引擎 _on_msg_callback，正则 ^「(.+?)」 提取引用块，组装 fly-pigeon 兼容结构
📍 engines/wecom_aibot.py · _on_msg_callback()
回调匹配会话：storage.handle_callback 优先按 short_id 匹配； 匹配不到再按 chat_id 找等待中的会话（唯一则命中，多个则 FIFO 降级），add_reply 挂到 session，状态置 replied
📍 storage.py · handle_callback()
轮询拿到回复 → 返回 Agent：hitl-mcp 轮询到 has_reply=true，把回复文本包成 { status: 'success', replies: [...] } 返回，Agent 继续执行
📍 mcp-server-ts/src/server.ts · resultToContent()

六、本地单机版 vs 公众机器人版（远程服务版）

同一套代码，通过环境变量切换形态。关键差异：

维度本地单机版公众机器人版（远程服务版）
部署位置 开发者本机 127.0.0.1:8081（brew/systemd 托管） 远程服务器，nginx 反代，公网或内网可达
Bot 归属 通常每人一个 / 自用 全公司共用一个企微 AI Bot（公众机器人）
HITL_SHARED_MODE false（默认） true
/api/* 鉴权 可选（未配 key/tokens 则放行，向后兼容） 强制：必须配 HITL_API_KEY 或 HITL_API_TOKENS
chat_id 缺省行为 回退到「最近活跃收件人」 直接拒绝，必须显式指定 --chat-id
多租户隔离 无（单用户） API Token → chat_id 白名单；会话按 short_id（全局唯一）精确匹配
新用户接入 管理台扫码 / 填凭证 企微给 bot 发条消息 → 自动回告 chat_id → 填进 MCP 配置即可
凭证持有 用户自己持有 bot_id/secret 运维统一持有；用户 MCP 只带 --api-key + --chat-id
MCP 关键参数 --service-url http://localhost:8081 --shared --api-key <key> --chat-id <id> --service-url https://hil.example.com

MCP 客户端配置示例（公众机器人版）

{
  "mcpServers": {
    "hitl-mcp-shared": {
      "command": "npx",
      "args": [
        "-y", "hitl-mcp",
        "--engine", "wecom-aibot",
        "--service-url", "https://hil.example.com",
        "--shared",
        "--api-key", "<运维分配的 token>",
        "--chat-id", "<你的 chat_id>",
        "--project-name", "my-project"
      ],
      "env": { "http_proxy": "", "https_proxy": "", "all_proxy": "" }
    }
  }
}

HITL_HOST=127.0.0.1          # 由 nginx 反代到公网，不直接暴露
HITL_PORT=8081
ENABLE_WECOM_AIBOT_ENGINE=true
WECOM_AIBOT_BOT_ID=<公众机器人 ID>
WECOM_AIBOT_BOT_SECRET=<公众机器人 Secret>

HITL_API_KEY=<单一可信 key>
# 或多租户白名单：

DATABASE_URL=sqlite+aiosqlite:///./data/service.db

七、可靠性与安全要点

连接可靠性

  • 断线指数退避重连：_run_loop 从 5s 起步，翻倍至 60s 上限
  • 应用层心跳：每 30s 发 ping，绕开 nginx 的协议级 ping 超时
  • 读循环前置：先启动 _reader_loop 再等订阅响应，避免死锁
  • disconnected_event 监控：同凭证多连接互踢时仅告警，由运维排查
  • 凭证落盘：WecomAibotStore 原子写 wecom_aibot_store.json，重启自动恢复

安全边界

  • API 鉴权：共享模式强制 Bearer Token，防冒充任意 chat_id
  • chat_id 白名单：token 绑定可发 chat_id，越权 403
  • 收件人锁定：共享模式禁止回退，防 A 的消息发到 B
  • 管理台：JWT 账号密码保护，动态注册接口同样受 API Token 保护
  • 会话隔离：靠 short_id 全局唯一精确匹配，引用回复杜绝多会话串扰
